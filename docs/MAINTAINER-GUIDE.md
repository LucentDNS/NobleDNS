# NobleDNS Maintainer Guide

> Intended audience: NobleDNS maintainers  
> Project status: Publicly maintained  
> Release model: Public artifacts are updated after the main branch passes automated validation

## 1. Maintenance Principles

NobleDNS aims to remain lightweight, stable, auditable, and compatible while keeping its rules effective.

Follow these principles when maintaining the project:

1. Do not add upstream sources merely to increase the rule count.
2. Do not change the semantics of existing rules without justification.
3. Do not convert complex rules into simple rules when their semantics cannot be confirmed.
4. Only simple upstream exception rules supported by the parser and validated as hostnames may enter the main subscription. Complex or unsupported exceptions must be excluded.
5. Never bypass drift detection, rule-count limits, or output validation.
6. All important changes must pass local validation or GitHub Actions validation.
7. Do not claim production-grade quality without supporting evidence.

## 3. Current Upstream Sources

The project currently uses exactly two upstream sources:

| Source | Purpose |
|---|---|
| AdGuard DNS Filter | DNS advertising and tracking protection |
| HaGeZi Multi Normal | General DNS advertising and tracking protection |

Configuration file:

`config/sources.json`

Current rule limit:

`500,000`

Do not add, remove, or replace an upstream source without a complete evaluation.

When evaluating a new source, record:

- Source and maintainer.
- License and third-party rights.
- Overlap with existing sources.
- Number of rules added and removed.
- Impact on false-positive risk.
- Impact on build resources and subscription size.

## 4. Routine Maintenance Workflow

### 4.1 Check Repository Status

In PowerShell:

```powershell
cd C:\NobleDNS
git status -sb
git pull --ff-only origin main
```

Confirm that there are no unresolved local changes in the working tree.

### 4.2 Update Upstream Sources and Build Locally

```powershell
py -3.12 .\update.py --out .\build-output --previous-manifest .\dist\manifest.json
```

If the network requires a proxy, explicitly specify a trusted HTTP/HTTPS proxy endpoint. The proxy URL must not contain credentials, a path, a query string, or a fragment. When `--proxy` is omitted, the builder does not read system proxy environment variables. Source URLs must remain HTTPS, and HTTPS-to-HTTP redirects are rejected. GitHub Actions must not depend on a proxy configured on a maintainer's personal computer.

```powershell
py -3.12 .\update.py --proxy http://127.0.0.1:7897 --out .\build-output --previous-manifest .\dist\manifest.json
```

Build output is written to:

`build-output/latest/`

If the build fails, do not copy the failed output into `dist/`.

### 4.3 Inspect Build Results

Pay particular attention to these files:

| File | What to inspect |
|---|---|
| `dns-filter.txt` | Main filtering rules |
| `manifest.json` | Sources, counts, hashes, and build metadata |
| `validation-report.txt` | Build validation report |
| `parser-exclusions.csv` | Excluded rules and their reasons |
| `badfilter-audit.csv` | Supported `$badfilter` directives, exact targets, outcomes and affected sources |
| `allowlist-active.txt` | Simple upstream exception rules included in the main subscription |
| `sources/sources-manifest.json` | Upstream snapshots and SHA256 hashes |

In particular, verify that:

- The total rule count does not exceed 500,000.
- Both upstream sources were fetched successfully.
- Source rule counts have not changed unexpectedly.
- Addition and removal ratios are reasonable.
- Exclusion reasons have not increased abnormally.
- The main subscription contains blocking rules and simple upstream exceptions that passed syntax and hostname validation; complex exceptions remain excluded.
- The build SHA256 matches the manifest.

### 4.4 Run Regression Tests

```powershell
py -3.12 -m py_compile .\update.py
py -3.12 -m unittest discover -s tests -v
git diff --check
```

Note: these commands do not check untracked files by default. For new documentation, also check UTF-8 encoding, the final newline, and trailing whitespace separately.

All tests must pass. The real-upstream leading-dot rule fixture (`tests/fixtures/leading-dot-rules.txt`) must verify that 27 valid rules are preserved with subdomain-only semantics and the malformed trailing-dot record is rejected by domain validation. AdGuard DNS documents `.domain^` and `.domain` as matching subdomains only, not the apex. Never rewrite these rules as `||domain^`.

#### Adding a Regression Case

Whenever a confirmed issue should become a regression case, follow these steps:

1. Append the hostname to `tests/fixtures/essential-domains.txt` if it must remain accessible and must not be blocked, or to `tests/fixtures/known-ads.txt` if it must remain blocked. Use one unique hostname per line; do not add filter-rule syntax.
2. Update the corresponding fixture count assertion in `test_fixture_sizes_are_explicit_and_stable` in `tests/quality_gates.py`. The current baselines are 72 essential-service hostnames and 20 known-ad hostnames.
3. Run the focused quality-gate tests:

   ```powershell
   py -3.12 -m unittest discover -s tests -p "quality_gates.py" -v
   ```

4. Commit the fixture file and its count assertion together. In the pull request, explain the new hostname and why it belongs in that fixture category.

The count assertions are intentionally pinned. Any fixture-size change must be explicit in code review so that test coverage cannot drift through unnoticed additions or removals.

### 4.5 Review Rule Changes

Do not review changes by looking only at the total rule count.

Compare:

- Added rules.
- Removed rules.
- Upstream source changes.
- Changes in overlap between the two sources.
- Changes in complex-syntax exclusions.
- Changes in the number of excluded leading-dot rules (`.domain^`, `.domain`).
- Exception-rule changes and whether those rules entered `allowlist-active.txt`.
- `$badfilter` directives: exact target, whether it was removed, and which approved source sets were affected.
- Confirm that every entry in `allowlist-active.txt` also appears in the main subscription, and compare the result with `active_exception_rules` in the manifest.

For large changes, preserve the upstream snapshots and build output for a separate review.

## 5. Anomalous Changes and Drift Protection

The builder uses a default drift threshold of 15% and performs two types of checks.

### 5.1 Upstream Source Rule-Count Changes

- For each upstream source, compare the current number of parsed `simple_block_rules` with the number recorded in the previous manifest.
- Calculate the percentage change using the previous count as the baseline.
- If either source exceeds the threshold, the build fails.

### 5.2 Main Subscription Rule Changes

- Compare the current merged rules with the previous `dns-filter.txt`.
- Calculate the percentage of added rules and removed rules separately.
- If either percentage exceeds the threshold, the build fails.
- Both percentages use the previous main-subscription rule count as the baseline.

If the previous manifest does not exist or is not supplied, drift checks are skipped. If the manifest's directory does not contain the corresponding `dns-filter.txt`, the upstream count check can still run, but the main-subscription rule-difference check cannot.

### 5.3 Previous Published Baseline

For routine builds, use the previous published baseline:

```powershell
py -3.12 .\update.py --out .\build-output --previous-manifest .\dist\manifest.json
```

`--previous-manifest` should point to the `manifest.json` from the previous published build. Its directory should also contain the matching `dns-filter.txt` so that both types of drift checks can run.

Do not use an unreviewed temporary build as the published baseline.

### 5.4 Manual Review of Large Changes

Pause the build-and-release process and investigate if any of the following occurs:

- A large change in upstream rule count.
- An abnormal increase in main-rule additions.
- An abnormal increase in main-rule removals.
- Incomplete upstream downloads.
- Invalid UTF-8 encoding.
- Invalid output rules.
- A total rule count above 500,000.

Only after confirming that the upstream changes are genuine and reasonable, and completing a rule-difference review, may a maintainer manually override the drift checks:

```powershell
py -3.12 .\update.py --out .\build-output --previous-manifest .\dist\manifest.json --allow-large-change
```

`--allow-large-change` skips the two drift checks described above. It does not disable other input checks, parsing checks, rule-count limits, or output validation.

A manual override must be documented in the maintenance record, including the reason, review findings, and decision.

Never remove a protection gate merely to make a build pass.

### 5.5 Local Build Artifacts

The default build output is `build-output/latest/` and contains, among other files:

```text
build-output/
└── latest/
    ├── dns-filter.txt
    ├── manifest.json
    ├── validation-report.txt
    ├── parser-exclusions.csv
    ├── badfilter-audit.csv
    ├── allowlist-active.txt
    └── sources/
        └── sources-manifest.json
```

`sources/sources-manifest.json` belongs to the local build output. Do not assume that this file already exists under the repository's current `dist/` directory.

After a build, inspect the reports and rule changes before deciding whether to update the public release artifacts. The builder also generates `build-output/latest/NobleDNS.txt`, which must be byte-for-byte identical to `dns-filter.txt`. The public release workflow synchronizes it to the repository root to preserve the legacy subscription URL.

## 6. Automated Workflow

Workflow file:

`.github/workflows/daily-build-release.yml`

Current automation behavior:

| Trigger | Behavior |
|---|---|
| Daily schedule | Build and validate; synchronize public artifacts when conditions are met |
| Push to `main` | Build, validate, and synchronize public artifacts |
| Pull request | Build and validate; do not publish |
| Manual run | Build and validate, then execute the public-release logic |

Daily scheduled time:

02:23 China Standard Time (UTC+8).

GitHub Actions uses UTC, so the cron expression is:

`23 18 * * *`

If an automated build fails, inspect the logs first. Do not repeatedly rerun it or bypass protections without understanding the failure.

## 7. Manually Changing Rules and Configuration

When changing upstream sources, the parser, filtering logic, tests, or workflows:

1. Confirm the purpose of the change.
2. Preserve the pre-change baseline.
3. Run syntax checks after making the change.
4. Run all unit tests.
5. Compare rule output before and after the change.
6. Inspect `git diff`.
7. Confirm that only intended files are included.
8. Commit and push.
9. Check GitHub Actions.

Never overwrite `dist/` without review.

## 8. Git Commit Conventions

Recommended commit prefixes:

| Type | Purpose |
|---|---|
| `feat:` | New feature |
| `fix:` | Bug fix |
| `refactor:` | Internal refactoring |
| `test:` | Test changes |
| `docs:` | Documentation changes |
| `ci:` | CI/workflow changes |
| `chore:` | Routine maintenance |

Before committing, run:

```powershell
git status --short
git diff --check
git diff
```

Stage, commit, and push only after reviewing the results.

Do not force-push unless explicitly authorized.

## 9. Network and Proxy Troubleshooting

If the GitHub HTTPS connection fails, first check:

```powershell
Test-NetConnection github.com -Port 443
Test-NetConnection 127.0.0.1 -Port 7897
```

If a local proxy is available, route a single Git operation through it:

```powershell
git -c http.proxy=http://127.0.0.1:7897 push origin main
```

This does not permanently change the global Git proxy setting.

## 10. Rollback Principles

If an incorrect commit is discovered:

1. Identify the problematic commit and its impact.
2. Check whether it has already caused a public rule change.
3. Prefer a new corrective commit or `git revert`.
4. Check the automation run history.
5. Confirm that the remote rules and local baseline are consistent.

Do not run `reset`, force-push, or rewrite history before confirming the remote state.

## 12. Project Quality Statement

NobleDNS is a publicly maintained DNS filtering rule set. A successful automated build means that the builder and implemented automated checks passed; it does not mean that every DNS client, website, and application has been individually tested in real-world conditions. Maintainers should continue reviewing rule changes, compatibility issues, and user feedback, and add confirmed issues to regression tests.

If a website or application is malfunctioning, a domain that should be blocked is not blocked, or another rule issue occurs, report it through GitHub Issues. Include the affected domain, website or application, DNS client and version, reproduction steps, and necessary sanitized DNS evidence.
